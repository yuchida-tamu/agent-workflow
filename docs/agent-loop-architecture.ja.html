プラットフォーム非依存のエージェント型開発ループ

GitHub 上に構築した、閉ループの開発ワークフローです。再利用可能なツールキットとして設計しています。コアがループを所有し、プラットフォームの知識（最初のパック: React Native Expo）とビジネスの知識（プロジェクトごと）は、いずれも注入されます。基本原則は既定で決定論的であること。スクリプトで行える手順はすべてスクリプトにし、エージェントは推論・判断・統合のためだけに取っておきます。そして各エージェント呼び出しは、その仕事をこなせる最も安価なモデルへとルーティングされます。

変わったこと: v0.8 → v1.0

v0.8 はプランでした。v1.0 は、このリポジトリ自身のバックログを動かしているループを記述します。この文書はいまや、出荷済みのコードと突き合わせて整合させてあります。あらゆるセクションと、配線グラフのあらゆるノードは、実在する挙動を反映しています。まだ仕様化されているが未実装のわずかなものは、現在形で記述するのではなく、そのように明示してあります。

v0.8 以降に着地したもの（決定論的、テスト済み）: リスクエンジン（事実／演算子パック、単調な義務の合併、ロックされたルール）。これには広げられた自己改変ガード（いまや利用側リポジトリが設置するワークフローである init/templates/** と actions/**、加えて policies/**、domains.yml、e2e/traces/** をカバー）と、ドメインマップの重要度という軸をついに機能させる高重要度ドメインのルールが含まれます。さらに、実行台帳と監査（agentflow-log）、統治ルールが不在は拒否である判定リーダー、G3 自動マージの権限レコード（PR は、人間を要さない判定のときにだけ自らをマージし、つねに記録を残します。偽の /approve を作ることは決してありません）、承認インボックスモジュール（G1／G2／G4 のキューと成果物の選定）、agentflow 自身の GitHub App アイデンティティ（作業は App として、判断は人間として。ボットの承認はコードで拒否）、サブ Issue 階層のリーダー（GitHub ネイティブなサブ Issue と、Child of #N のテキストフォールバック。どちらが答えたかを報告）、release_kind のセマンティクス、ルーティングされたティアで動く 11 個のエージェント定義、そしてランナー上でのヘッドレスレビュー（ステージ 1）。

まだ仕様化されているが未出荷のもの: pack-expo のケイパビリティアダプター（run · verify · execute-step · ship）とスキル群。そのため、実際のアプリを駆動するもの（実装者のセルフ検証、UX レビューのピクセル、E2E のトレース派生と再生実行）は、コアには配線されているものの、パックがこれらの継ぎ目を実装するまで、端から端までは動きません。加えて、ヘッドレスディスパッチの起動（作られているが、あらゆる状態でオフ出荷）、夜間 QA のヘッドレス（保留。セルフホストの macOS ランナーが必要）、そしてインターフェースを真に検証する 2 つ目のプラットフォームパックです。

確定した決定事項

  • バックログの置き場所: GitHub Issues。 ラベルがステートマシンをエンコードし、コメントが承認を運びます（リリースゲートもその 1 つで、検証済みの /approve G4 として。その遷移は、承認したタグに追随します）。そして GitHub Actions がイベントバスです。1 つのプラットフォームがすべての状態を保持します。
  • E2E モデル: エージェントがコンパイルし、決定論的に再生する。 Maestro は不採用（セレクタ保守の負担が重く、遅い）。シナリオは Gherkin で書き、エージェントが各ステップを一度だけ解釈してコンパイル済みトレースを出力します。ランナーはそれ以降、決定論的に再生します。トークンはスイートの規模ではなく、UI の変更に比例します。
  • プラットフォーム非依存のコア。 このリポジトリ（agent-workflow）はツールキットであってアプリではなく、プラットフォーム固有のものは一切含みません。プラットフォームの能力はパック（最初は pack-expo）へと抽出されます。どのプロジェクトも、コア + パックを設置すれば、プロジェクトごとの config でループ一式を得られます。
  • 決定論第一 + モデルルーティング。 下記の 2 つの基本原則が、配線図のあらゆる手順を統治します。
  • リスク基準は注入され、内部に取り込まれない。 ツールキットは決定論的なポリシーエンジンを出荷します。各プロジェクトは、ドメインマップ、ポリシールール、インテークの質問を通じて、自身のビジネスリスク基準を供給します。技術的なルーブリックは、既定のベースラインパックにすぎません。

3 層の知識モデル

3 種類の知識、3 人の所有者。リスクエンジンで実証されたのと同じ注入パターンが、あらゆる層の境界に適用されます。下位の層はメカニズムと継ぎ目を定義し、上位の層が知識を供給します。

  • コア — ループの仕組み（このツールキット）ステートマシン、GitHub の配線、ゲート G1–G4、ポリシーエンジンとプラットフォーム中立なベースラインルール、エージェントの陣容、振る舞いを記述するシナリオ DSL の文法とランナーのコア、卒業台帳、インストーラー。プラットフォームには無関心で、エージェントのプロンプトはケイパビリティを参照し、プラットフォームのツールを参照することはありません。
  • プラットフォームパック — この種のアプリをどう作り、どう駆動するかスキル群（expo-dev、mobile-verify、EAS の release）、E2E のステップ実行器（モバイルでは agent-device）、ビルド／配布のパイプライン、プラットフォームのハードトリガーとなるポリシールール（ios/**、SDK のバンプ、ネイティブ依存。これは文字どおり、もう 1 つのポリシーパックにすぎず、同じ単調な合併で結合されます）、そしてランナー要件（rn-expo はセルフホストの macOS ランナーを宣言します）。最初のパックは pack-expo。Web パックなら、同じ継ぎ目に Playwright を差し込むことになります。
  • プロジェクト — この製品が何で、何がリスクなのかドメインマップ、ビジネスポリシーパック、インテークの質問、このアプリのシナリオ、規約のオーバーライド、そして agentflow.config.json。config は自身のプラットフォームを宣言します: platform: rn-expo。

ケイパビリティインターフェース — コアが定義する継ぎ目

4 つのインターフェースが、コアとパックの間の契約のすべてです。コアのエージェントとスクリプトがこれらを消費し、パックがこれらを実装します。

インターフェース契約消費者rn-expo での実装
run観測可能な環境でアプリを起動する実装者、UX レビュアー、QA エクスプローラーExpo 開発サーバー + iOS シミュレータ
verify動作中のアプリを駆動し、証跡（スクリーンショット、ログ）を取得する実装者のセルフ検証、UX レビュアーagent-device
execute-stepコンパイル済みの 1 ステップトレースを決定論的に再生するE2E シナリオランナーagent-device のステップアダプター
shipビルド、配布、提出統合スクリプト + リリーススクリプトEAS のビルド／サブミット、TestFlight

初日から抽象化しすぎないこと: インターフェースをいま命名して仕様化するのは、定義するのが安価で、コアを清潔に保てるからです。v1.0 時点で 4 つの継ぎ目は interfaces/ に文書化されており、あらゆるコアの消費者がそれらを呼び出します。しかし pack-expo はまだアダプターを実装していません。packs/expo/ が出荷するのは、そのポリシーパックとランナー宣言だけです。パックが継ぎ目を埋めるまで、実際のアプリを駆動するものはすべて不活性です。継ぎ目を真に検証するのは 2 つ目のパック（おそらく Web）であり、それは、最初のパックに対してループが端から端まで動くようになるまで待ちます。

基本原則 1 — 決定論のラダー

ループのあらゆる手順は、それを確実にこなせる最も低い段に置かれます。ある手順が段を 1 つ上がるのは、その下の段が結果を判断できないことが実証されたときだけです。決定論的なチェックはつねに、どのエージェントも呼ばれる前に走ります。無料のチェックが弾いたはずの作業に、トークンを費やしてはいけません。

  • スクリプトと静的チェック — トークンゼロ構造化データに対するルールで判断できるものすべて。状態遷移、ラベル管理、テンプレート検証、依存関係チェック、リント／型チェック／単体テスト、ワークツリーの準備、E2E シナリオの実行、構造化レポートからの Issue 起票、バージョンのバンプ、変更履歴、EAS サブミット。
  • 小型モデル（Haiku）— 境界のある分類明確なルーブリックに照らして分類・抽出・要約し、誤答が安価に検出・修正できるもの。Issue のトリアージ、重複検出、diff の要約、E2E 失敗のクラスタリング、リスクスコアのタイブレーク。
  • 中型モデル（Sonnet）— プランの範囲内でのコード承認済みプランに対するコードの記述・変更、テストの作成、修正ループ、探索的な QA パス、E2E トレースのコンパイル。主力ティアです。
  • フロンティアモデル（Opus / Fable）— 答えの定まらない判断曖昧な意図からのブリーフのシェイピング、アーキテクチャプラン、タスク分解、独立したコードと UX のレビュー、レビュー所見の敵対的検証、何かが行き詰まった理由の診断。まれで、意図的で、それだけの価値があるもの。

エスカレーションのルール: ある手順が失敗したとき、段をちょうど 1 つだけ上がることができ、そのエスカレーションは理由とともに記録されます。機械的な作業のために、より上位のティアへルーティングされるものはなく、どのエージェントも、その手前にある決定論的なチェックが通る前には走りません。

リスクポリシー — ルーブリックではなく、エンジン

技術的なルールだけではリスクを見誤ります。チェックアウトフローへの 40 行の変更は、設定画面の 800 行のリファクタリングよりも重大です。しかしビジネスリスクはプロジェクト固有なので、ツールキットがそれをハードコードしてはいけません。切り分けはこうです。ツールキットは決定論的なポリシーエンジンを出荷し、リスク基準はプロジェクトが所有するデータとする。 3 つの層を一緒に評価し、後の層が権威を持ちます。

  • ポリシーエンジン — ツールキット汎用の、決定論的な評価器。宣言された面（プラン時）か実際の diff（PR 時）に、ブリーフの構造化フィールドを加えて受け取り、有効なあらゆるルールパックを評価して、単なるスコアではなく義務を出力します。
  • 技術ベースラインパック — ツールキットの既定ハードトリガー: ネイティブな面（ios/、app.config.*、eas.json）、SDK／RN のバンプ、ネイティブ依存、スキーマ／マイグレーション、シークレット、そしてワークフローファイルそのもの（エージェントが自分のゲートを緩めることはありません）。加算的な要因: 新規依存、広く import される共有モジュール、diff サイズ、テストなしで変更されたロジック。プロジェクトはそのすべてを拡張・再重み付け・オーバーライドできます。
  • ビジネスパック — プロジェクト所有、権威ありプロジェクトごとに書かれるドメインマップ、ポリシールール、インテークの質問。リスク判断が実際に宿るのはここです。ベースラインは、あらゆる RN Expo プロジェクトに共通するものを捉えるだけです。

ドメインマップ — ビジネス判断を一度だけエンコードする

要となる成果物。ビジネス上の能力をコードに対応づける、プロジェクト所有のファイルです。人間が重要度の判断をちょうど一度だけ下し（「チェックアウトはクリティカル、設定はそうでない」）、エンジンがそれを永遠に決定論的に強制します。これこそが、ビジネスを踏まえたゲーティングを L0 の段に保つものです。

# domains.yml — ツールキットではなく、プロジェクトが所有する
checkout:
  description: "Purchase flow from cart through receipt"
  criticality: critical        # ビジネス上の判断。人間が、一度だけ下す
  paths: ["src/features/checkout/**"]
  screens: ["/checkout/*"]
  scenarios: ["@checkout"]     # E2E シナリオのタグ
onboarding:
  criticality: high
  paths: ["src/features/onboarding/**"]

同じマップは、ループ全体で無料で再利用されます。マージ後のスモークは、触れたドメインのシナリオタグを走らせ、UX レビュアーはどのドメインの受け入れ基準が適用されるかを知らされ、変更履歴はドメインごとにグループ化され、信頼の卒業は変更クラス×ドメインごとに追跡されます。あるクラスが settings では卒業していても、checkout ではまだ人間のゲートを要する、ということがありえます。

ポリシールール — スコアではなく、義務

# policies/business.yml — プロジェクト所有
rules:
  - when: domain.criticality == "critical"
    then: [require: G2, block: auto-merge, run: domain-scenarios-pre-merge]
  - when: brief.compliance_impact == true
    then: [require: G2, notify: reviewer]

エンジンの判定は、一連の帰結です。G2 を要求する、自動マージをブロックする、追加シナリオを走らせる、誰かに通知する。これらが要因ごとのコメントとして投稿され（監査可能）、ラベルとして適用されます（そのラベル自体が、ディスパッチのイベントになります）。ベースラインパックからの低／中／高のスコアは、ルールへの入力の 1 つにすぎなくなります。

インテークの質問 — ビジネスリスクを源泉で宣言する

各プロジェクトは、Product Shaper がインテークのヒアリング中に尋ねるべきビジネスインパクトの質問を注入します。この変更は、ユーザーが支払うものや、価格について目にするものを変えるか。個人データに触れるか。ユーザーにとってその挙動の変化は不可逆か。答えはブリーフ上の構造化フィールドとなり、上記のルールが決定論的に消費します。アイデアを持つ人は、どんな diff 解析よりも、変更のビジネス上の意味をよく知っています。

相互チェックのドリフト検出: ブリーフが宣言したインパクトと、diff のドメインフットプリントは一致しなければなりません。ブリーフが revenue_impact: false と言ったのに、PR が checkout ドメインに着地したなら、エンジンはその矛盾を検出してエスカレートします。ブリーフが誤っていたか、実装がさまよったかのどちらかです。どちらにせよ、プラン対 diff のスコープチェックと同じく、決定論的です。

未対応づけのコードは、プロジェクトごとのポリシー上の選択であり、エンジンは既定の立場を取りません。unmapped_criticality は既定で null の config 値で、その場合、未対応づけのファイルは変更の重要度に何も寄与しません（そして、対応づけの元となる domains.yml が存在して初めて適用されます）。未対応づけのコードを勘定に入れたいプロジェクトは、その値を設定するか、記録される Haiku 呼び出しに、ドメインの説明に照らして変更を分類させます（ルーティングポリシーに沿って。そしてマップを育てる後押しにもなります）。エンジンは domains.unmapped_fraction を第一級の事実として表面化させます。コアにハードコードされた閾値はありませんが、プロジェクトが腐敗検出のルールをゼロから書く必要はありません。インストーラーが unmapped_warn_fraction（テンプレート既定値 0.2）を出発点の config 値として出荷し、agentflow-init adopt --coverage がすでにそれを強制して、リポジトリの未対応づけの割合が自分で設定した予算を超えるたびに警告します。

ポリシーパックのスキーマ — すべてに 1 つのルール形状

ハードトリガー、加算的なスコア要因、ビジネスルールは、すべて同じルール形状です。違うのは、どの義務を出力するかだけ。これがエンジンを小さく保ち、技術的であれビジネス的であれ、あらゆる基準を等しく注入可能にします。

# policies/business.yml
pack: my-app-business
version: 1
rules:
  - id: critical-domain
    description: "Critical business domains always get human plan review"
    stage: both                  # plan | pr | both
    when:
      all:
        - fact: domains.max_criticality
          in: [critical]
    then:
      require: [G2, human-merge]
      block: [auto-merge]
      run: [domain-scenarios]    # 触れたドメインの @tag が pre-merge で走る

  - id: native-surface           # 「ハードトリガー」も、ただのルール…
    when: { fact: diff.files, matches: ["ios/**", "app.config.*"] }
    then: { floor: high, require: [G2], block: [auto-merge] }

  - id: large-diff               # …そして「加算的な要因」もまた然り
    when: { fact: diff.loc, gte: 800 }
    then: { score: +4 }

条件は、構造化された事実／演算子のツリーです。閉じた演算子集合（is、in、gte、lte、contains、matches、exists）に対する all / any / not。パースすべき式言語はありません。あらゆるパックは、走る前に JSON Schema で検証でき、評価は自明に決定論的です。読みやすい文字列のシュガーは、必要になれば後からこの形式へコンパイルできます。

義務は、意図的に閉じた 7 つの動詞の語彙です。require（G2、human-merge）· block（auto-merge）· run（シナリオタグ／名前付きチェック）· notify · label · score: +N · floor: <level>。スコアからレベルへの閾値と、レベルごとの既定義務は config に置かれ、加算的な層を同じ語彙に差し込みます。

history.*class_graduated — 変更クラス×ドメインごと、卒業台帳からPR のみ
score.*、meta.*score.total、meta.stage、meta.change_class、meta.maturity（genesis | steady）両方

合併こそが安全性の性質: 義務は合併されるだけです。より多くのパックを評価しても、制約を追加することはあっても、取り除くことは決してありません。だから、推論すべき優先順位の演算はありません。緩めることは明示的でスコープが限られます。プロジェクトパックは、ベースラインのスコアリングルールを id 単位で disable したり再重み付けしたりできますが、ツールキットが locked: true と印を付けたルール（ワークフローとポリシーファイル自体に対する自己改変ガード）は、どのパックも無効化できません。エージェントも — config も — 自らの檻を開けることはできません。

パックはテスト可能です。 評価は純粋（事実を入れ、判定を出す）なので、パックはフィクスチャテスト付きで出荷され、agentflow policy test で走ります。例となる事実集合に対して、期待される義務をアサートします。これが、プロジェクトが安全にリスクポリシーを進化させる方法です。ルールを厳しくし、フィクスチャを走らせ、過去のどのシナリオがいまなら別のゲートを通るかを、正確に見ます。ポリシーファイルの変更自体が locked ルールの領域なので、それらはつねに G3 で人間を通過します。

tests:
  - name: "checkout copy change still blocks auto-merge"
    facts: { diff: { files: ["src/features/checkout/Receipt.tsx"], loc: 4 } }
    expect: { block: [auto-merge] }

判定は決定論的な JSON ドキュメントです。評価されたあらゆるルール、マッチした事実、義務の合併、結果として得られるレベルを含み、要因ごとのコメントとしてレンダリングされ、risk:* ／義務のラベルとして適用されます。そのラベル自体が、次のステージへのディスパッチイベントです。同じエンジンを 2 回走らせます。プラン時は plan.* + brief.* に対して、PR 時は diff.* に対して。PR 時には drift.* の事実が有効になります。

配線 — 対話的

GitHub がイベントバスです。下の各列は 1 つのステージで、GitHub のイベントによって左から右へトリガーされ、決定論的なスクリプト、次にマイクロエージェント、次にフルのエージェントへと下へ流れ、人間のゲートがあるところでそこに至ります。任意のノードをクリックすると、それが何をするか、なぜラダーのその段に位置するか、そして何を出力するかが分かります。破線のティール色のエッジは、ループが閉じるところです。QA の所見が、新しい Issue としてインテークに再び入ってきます。このグラフは、ループを pack-expo でインスタンス化したものを示します。ノードがシミュレータ、agent-device、EAS と言っているところは、それがコアの前提ではなく、パックによるコアのケイパビリティインターフェースの実装です。v1.0 時点で、それらのパックアダプターは仕様化されているがまだ作られていないので、実際のアプリを駆動するノード（実装者のセルフ検証、UX レビュー、E2E ランナー）は、今日端から端まで動くものではなく、意図された姿を記述しています。

このグラフの読み方

各列はステージ、各行は決定論のラダーの段です。作業はつねに、GitHub のイベント（最上段）を通じて列に入り、トークンが費やされる前にあらゆる決定論的チェックを通過します。ノードを選択すると（クリック、または Tab + Enter）、その詳細がここに表示されます。

入口の経路 — プロジェクトはどうループに到達するか

ループは定常状態の機構です。あらゆるステージはベースラインに対して決定論的です。ドメインマップ、規約、CI、起動可能なアプリ。そのベースラインを確立することはステージではありません。それはループの前に、3 つの経路のいずれかで一度だけ起こります。

  • Genesis — 新しいプロジェクト一発の project-genesis エージェント（Opus）。セッション内で人間にヒアリングし（多肢選択）、次にループの前提条件を確立します。アプリの骨格、リポジトリ + ラベル、インテークの質問を含む config、規約のドキュメント、ドメインマップ v0、CI。そしてマイルストーン 1 の Issue を state:idea でバックログに投入します。その投入されたバックログが引き継ぎです。genesis は終了し、agentflow-next が Issue #1 を拾い、ループがその後のすべてを所有します。
  • Adoption — 既存のアプリagentflow-init project と、コードベースの構造からドメインマップの草案を提案する adoption-audit エージェント。人間が各重要度を確認します（人間のままであるべき唯一の判断）。既存の規約は、発明されるのではなく、読み取られます。
  • 定常状態 — すでにループの中上で配線した 6 つのステージ。

成熟度はモード切り替えではなく、事実: config が maturity: genesis | steady を宣言し、meta.maturity としてポリシーエンジンに表面化されます。あらゆる変更が新しい画面、新しい依存、新しいドメインである若いプロジェクトは、定常状態のスコアリングでは窒息してしまいます。genesis のあいだ、パックはスコアリングルールを和らげ、G2 をロックされたトリガーのために取っておきます。一方で自動マージは、いずれにせよ不可能なままです。steady への切り替えは、それ自体が意図的な人間の判断です。基盤が定まったと宣言する、その瞬間です。

人間との接点

  • G1
    ブリーフ承認シェイプされた Issue への /approve コメント。軌道修正に最も安価な場所。
  • G2
    プラン承認リスクエンジンの義務がそう言うときにのみ必要。プロジェクト自身のドメインマップとポリシールールが駆動する。些細な修正はそのまま流れる。
  • G3
    マージ承認agent_identity が agentflow に、作業の作成者となる独自の GitHub App を与えているところではネイティブな PR レビュー。そうでないところでは、SHA を明記した /approve コメント。GitHub は自分の PR の承認を禁じるため。adopt --verify が、リポジトリがどのモードにあるか、そしてその理由を報告する。実証された低リスクのクラスは、ラベル駆動の自動マージへと卒業していく。
  • G4
    リリース承認検証済みの /approve G4 コメントはリリースを承認するが、意図的にラベルを動かさない。agentflow-release がそれから注釈付きタグと GitHub Release を作成し、そのリリースが存在して初めて verified → released の遷移を行う。ラベルは成果物に追随するので、state:released が、その裏に何もない状態で真になることは決してない。release_kind が、この経路が走るのか、パックの ship アダプターが走るのか、あるいはそのアイテムがすでに終端だったのかを決める。

常設のルール: どのステージでもいつでも割り込めます。あらゆるエージェントは、境界付きリトライを使い切ったとき、空回りする代わりに通知でエスカレートします。沈黙はつねに進行を意味し、決して停滞ではありません。そしてゲートは、人間のいる場所で人間に会いに行きます。対話的なセッションでは、エージェントは多肢選択のプロンプトで判断を集め、人間自身の gh アカウントを通じて /approve の成果物を投稿します。記録は GitHub であって、会話ではありません。コメント駆動の承認は、非同期の経路として残ります。純粋な承認インボックスモジュールが、いま G1、G2、G4 で待っているすべてを集め、各アイテムを、それが照らして判断されるべき正確な成果物（ブリーフ、プラン、リリースのコメント）と対にし、成果物のないアイテムを提示することを拒みます。だから、キューをさばく人間が、誰も書いていないブリーフを承認してしまうことはありません。G3 は、そのキューから意図的に欠けています。マージは diff によって判断されるものであって、リストからではないからです。

作業と判断は、作成者が異なります。 エージェントは作業を作成します。ブランチ、コミット、PR、レビューと判定のコメントを、agentflow の GitHub App として。人間は判断を作成します。/approve、レビュー承認、マージを。これは合意ではなく強制されています。ゲートバリデーターは、承認者リストを参照する前に、ボットが作成したいかなる承認も拒み、approvers は人間のログインだけとして検証されます。例外は 1 つ存在し、その権限はエージェントのものではなくエンジンのものです。記録済みのリスク判定がすでに human-merge を持たず、auto-merge のブロックも持たず、マージされる head を明確に記述している PR に対する G3 です。それはまさに、ループがすでに無人でマージする条件なので、App は判断を発行するのではなく、書き写します。これを裁定する判定リーダーは、たった 1 つのルール — 不在は拒否 — に基づきます。判定が欠けているか、パースできないか、SHA を持たないか、別のコードに対して計算されたものなら、何も承認しません。そしてループが無人でマージするとき、それはマージを先に記録してからマージし、何がそれを許したかを名指す権限レコードを残します。そのレコードは、/approve の行に決して似ないよう、構造上禁じられています。App はどこでも任意です。App のないリポジトリは、人間自身の認証で同じループを走らせます。

E2E モデル — 一度コンパイルし、永遠に再生する

シナリオは Gherkin で書かれます。振る舞いを表し、読みやすく、タグ付き（@checkout はドメインマップに束縛され、@smoke はマージ後のサブセットを印します）。この振る舞いの層の下には、人間が書かないコンパイル済みの成果物があります。

  • 初回 — エージェントが解釈する（L2）。 Sonnet のエージェントがステップ（「ユーザーがチェックアウトをタップしたとき」）を読み、パックの verify プリミティブを通じてアプリを駆動し、コンパイル済みトレースを出力します。解決されたセレクタ（固定の解決順: testID → アクセシビリティラベル → 可視テキスト）を伴う、順序付けられたプリミティブなアクション、待機、アサーション。トレースは e2e/traces/ にコミットされます。バージョン管理され、レビュー可能なコードです。
  • それ以降のあらゆる実行 — 決定論的な再生（L0）。 ランナーはトレースをドライバーに対して直接再生します。ループの中にモデルはなく、速く、トークンゼロ、同一の判定。これが夜間スイートです。
  • 再生失敗 — ラダーが決める。 trace-deriver エージェントがステップを再派生します（1 段のエスカレーション、記録あり）。成功すれば、UI は変わったが振る舞いは保たれています。トレースは PR 経由で更新され、それは G3 を通るので、アサーションをこっそり弱めるトレースも、なお人間に会います。エージェントも失敗すれば、振る舞いが壊れています。証跡バンドル → トリアージ → Issue としてインテークへ。

v1.0 の状況: ランナーのコアは作られてテスト済みです。Gherkin のパーサー、タグ選択、execute-step アダプター上でのトレース再生、needs-derivation の発行。そして trace-deriver エージェントは定義済みです。しかし、トレースをコンパイルすること（verify の駆動）も、それを再生すること（execute-step の駆動）も、プラットフォームパックのアダプターを通じて走り、pack-expo はまだそれらを実装していません。だからこのモデル全体は、仕様化されコアに配線されてはいますが、パックが継ぎ目を埋めるまで、端から端までは走りません。

経済性: トークンは、新しいシナリオと変わった UI にのみ費やされます。スイートの規模ではなく、変更に比例します。変わっていないアプリでの 50 シナリオの夜間実行は、何もかかりません。そして「不安定なセレクタ」対「本物の回帰」が、判断ではなく決定論的な区別になります。

ツールキットのパッケージング — コア、パック、プロジェクト

知識の層ごとに 1 つ、3 つの成果物。インストーラーは、プロジェクトをコアと、宣言されたプラットフォームパックに配線し、両者のバージョンをピン留めします。実質的なものはすべて、1 か所でアップグレードされます。

agent-workflow/                     # コア — このリポジトリ、プラットフォームに無関心
├── actions/          # 複合 GitHub Actions: gate-check · risk-verdict · dispatch · post-merge · auto-merge
├── scripts/          # state · policy engine · facts · gate validator · verdict reader · log (ledger/audit) · release · identity · hierarchy · next · e2e
├── policies/         # プラットフォーム中立なベースラインパック（diff サイズ、共有モジュール、テスト、広げた自己改変ガード、高ドメインルール）
├── scenarios/        # 振る舞いの DSL 文法 + ランナーのコア（実行器に非依存）
├── agents/           # 11 個の定義: product-shaper · architect · implementer · code/ux reviewers (Opus) · sentinel · qa-explorer · trace-deriver · triage · project-genesis · adoption-auditor
├── interfaces/       # run · verify · execute-step · ship — コア↔パックの契約
└── init/             # インストーラー: アプリのリポジトリをコア + 宣言されたパックに配線

packs/expo/                         # プラットフォームパック — React Native Expo
├── policies/         # ✅ プラットフォームのハードトリガー: ios/**、app.config.*、SDK バンプ、ネイティブ依存
├── runners.yml       # ✅ 宣言: シミュレータのジョブ向けセルフホスト macOS ランナー
├── skills/           # ⏳ 仕様化済み、未実装: expo-dev · mobile-verify · release (EAS)
└── adapters/         # ⏳ 仕様化済み、未実装: run/verify → シミュレータ + agent-device · execute-step · ship → EAS

your-app/                           # プロジェクト — 利用側の任意のリポジトリ
├── .github/workflows/agentflow-*.yml   # ピン留めしたコアの Action を呼ぶ薄いスタブ
├── agentflow.config.json               # platform: rn-expo · インテークの質問 · モデルのオーバーライド
├── domains.yml                         # ビジネス能力 → コードのマップ + 重要度
├── policies/business.yml               # このアプリのリスクルール（権威あり）
└── e2e/scenarios/*.feature             # このアプリの振る舞いのシナリオ

アプリごとの config は、プロジェクトが異なる場所です。夜間のスイープがどのフローを歩くか、G2 にとって何が高リスクとみなされるか、どの変更クラスが自動マージできるか、そしてモデルティアのオーバーライド。ステートマシン、エージェント、インターフェースはどこでも同一です。それが、それらを決定論的で、ルーブリック駆動で、プラットフォームに無関心に保つことの見返りです。

導入の道のり — クロール、ウォーク、ラン

フェーズ 1 · クロール — 出荷済み

スクリプト + 手動ディスパッチ

L0 の層。ステートマシンの CLI、ラベル、ゲートバリデーター、リスクエンジン + 事実、判定リーダー、実行台帳、E2E ランナーのコア、agentflow-next。作られてテスト済み。エージェントは /next 経由で 1 つのローカルセッションから走る。これが、今日このリポジトリ自身のバックログを動かす、決定論的な骨格。

フェーズ 2 · ウォーク — おおむね出荷済み

Actions 駆動 + 並列

11 個のエージェント定義、インストーラー（init labels/project/adopt）、App アイデンティティ、複合 Actions（gate-check、risk-verdict、dispatch、post-merge、auto-merge）は出荷済み。まだ未着手: 実装者が並列のワークツリーでセルフ検証できるようにする pack-expo アダプターと、最初の実際の利用側アプリでのループ実行。セルフホスト macOS ランナーでの夜間 QA はコストの都合で保留。

フェーズ 3 · ラン — 部分的

段階的な自律

実証された変更クラスの判定ゲート付き自動マージと、低リスクプランの G2 自動通過は出荷済み。インストーラーは数分でリポジトリをループ対応にする。ヘッドレスレビュー（ステージ 1）は今日ランナー上で走る。ヘッドレスディスパッチの起動は作られているが、あらゆる状態でオフ出荷。ケイパビリティの継ぎ目を真に試す 2 つ目のプラットフォームパック（Web）は、まだこの先。

ビルド状況 — v1.0

決定論的なコアは作られ、テストされ、このリポジトリ自身のバックログを動かしています。残るのは、プラットフォームパックと、レビューより先のヘッドレスなステージです。未対応づけのコードは、コアに組み込みの既定を持ちません。unmapped_criticality はプロジェクトごとの config 値（既定 null — 寄与なし、domains.yml が存在するところにのみ適用）で、domains.unmapped_fraction は、プロジェクトがゲートにできる第一級の事実です。Haiku による分類はプロジェクトごとのオプトイン。インストーラーはそうしたゲートを 1 つすでに出荷しています。unmapped_warn_fraction（テンプレート既定値 0.2、adopt --coverage が強制）。だから腐敗検出は、ゼロから書くルールではなく、調整する config の数字です。ランナーの構成: セルフホストの Mac 1 台。GitHub Actions の concurrency グループでキューイングされます（シミュレータのジョブは 2 に上限）。スケールのトリガーは機械的で、キューの待ち時間の中央値が約 10 分を持続的に超えたら 1 台足します。インターフェースのシグネチャは interfaces/ に仕様化されています。各アダプターは実行可能ファイルで、stdin/stdout の JSON、共有された終了コード（0 正常 · 10 回復可能 · 20 致命的）が、その上の境界付きリトライのスクリプトに流れ込みます。ただし、まだどのパックもそれらを実装していません。E2E: 上記のコンパイル&再生モデル。コアは完成し、それらのアダプターを待っています。
