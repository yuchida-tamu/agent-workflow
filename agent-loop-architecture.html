A Platform-Agnostic Agentic Development Loop

A closed-loop development workflow built on GitHub, designed as a reusable toolkit. The core owns the loop; platform knowledge (first pack: React Native Expo) and business knowledge (per project) are both injected. Ground rule: deterministic by default — every step that a script can perform is a script; agents are reserved for inference, judgment, and synthesis, and each agent call is routed to the cheapest model that can do the job.

Event  GitHub webhook / schedule Script  deterministic, zero tokens Agent  model-routed inference Gate  human decision

What changed: v0.8 → v1.0

v0.8 was a plan. v1.0 describes the loop that runs this repo's own backlog. This document is now reconciled against shipped code — every section and every wiring-graph node reflects behaviour that exists, and the few things that are still specified but not built are labelled as such rather than described in the present tense.

Landed since v0.8 (deterministic, tested): the risk engine (fact/operator packs, monotonic obligation union, locked rules) with a widened self-modification guard (now covering init/templates/** and actions/** — the workflows consuming repos install — plus policies/**, domains.yml, and e2e/traces/**) and a high-criticality-domain rule that finally makes the domain map's criticality axis load-bearing; the run ledger & audit (agentflow-log); the verdict reader whose governing rule is absence-is-refusal; the G3 auto-merge authority record (a PR merges itself only on a verdict that demands no human, and always leaves a record — never a forged /approve); the approval-inbox module (G1/G2/G4 queue + artifact selection); agentflow's own GitHub App identity (work as the App, decisions as the human, bot approvals refused in code); the sub-issue hierarchy reader (native GitHub sub-issues with a Child of #N text fallback, reporting which answered); release_kind semantics; the eleven agent definitions at their routed tiers; and headless review (stage 1) on a runner.

Still specified, not yet shipped: the pack-expo capability adapters (run · verify · execute-step · ship) and skills — so anything that drives the real app (implementer self-verify, UX review pixels, E2E trace derivation and replay execution) is wired in core but cannot run end-to-end until a pack implements the seams; headless dispatch launch (built, shipped off for every state); nightly QA headless (deferred, needs a self-hosted macOS runner); and the second platform pack that truly validates the interfaces.

Decisions locked in

  • Backlog home: GitHub Issues. Labels encode the state machine, comments carry approvals (the release gate among them, as a validated /approve G4 whose transition follows the tag it authorises), and GitHub Actions is the event bus. One platform holds all state.
  • E2E model: agent-compiled, deterministically replayed. Maestro is out (selector maintenance toil, slow). Scenarios are Gherkin; an agent interprets each step once and emits a compiled trace, which the runner replays deterministically ever after. Tokens scale with UI change, not suite size.
  • Platform-agnostic core. This repo (agent-workflow) is the toolkit, not an app — and nothing platform-specific lives in it. Platform capabilities are extracted into packs (pack-expo first); any project installs core + a pack and gets the full loop with a per-project config.
  • Determinism-first + model routing. The two ground rules below govern every step in the wiring diagram.
  • Risk criteria are injected, never internalized. The toolkit ships a deterministic policy engine; each project supplies its own business-risk criteria via a domain map, policy rules, and intake questions. The technical rubric is only a default baseline pack.

The three-layer knowledge model

Three kinds of knowledge, three owners. The same injection pattern proven by the risk engine applies at every layer boundary: lower layers define mechanisms and seams; upper layers supply the knowledge.

  • Core — how the loop works (this toolkit)The state machine, GitHub wiring, gates G1–G4, the policy engine and platform-neutral baseline rules, the agent roster, the behavioral scenario DSL grammar and runner core, the graduation ledger, the installer. Platform-blind: agents' prompts reference capabilities, never platform tools.
  • Platform pack — how this kind of app is built and drivenSkills (expo-dev, mobile-verify, EAS release), the E2E step executor (agent-device for mobile), the build/distribute pipeline, platform hard-trigger policy rules (ios/**, SDK bumps, native deps — literally just another policy pack, combined by the same monotonic union), and runner requirements (rn-expo declares the self-hosted macOS runner). First pack: pack-expo; a web pack would plug Playwright into the same seams.
  • Project — what this product is and what's risky about itThe domain map, business policy pack, intake questions, this app's scenarios, convention overrides, and agentflow.config.json — which declares its platform: platform: rn-expo.

Ground rule 1 — the determinism ladder

Every step in the loop is placed on the lowest rung that can do it reliably. A step only moves up a rung when the rung below demonstrably can't decide the outcome. Deterministic checks always run before any agent is invoked — never spend tokens on work that a free check would have rejected.

  • Scripts & static checks — zero tokensAnything decidable by rules over structured data: state transitions, label management, template validation, dependency checks, lint / typecheck / unit tests, worktree setup, E2E scenario execution, issue filing from structured reports, version bumps, changelogs, EAS submit.
  • Small model (Haiku) — bounded classificationClassify, extract, or summarize against a clear rubric where a wrong answer is cheap to detect and correct: issue triage, duplicate detection, diff summaries, E2E failure clustering, risk-score tie-breaks.
  • Mid model (Sonnet) — code within a planWriting and modifying code against an approved plan, authoring tests, fix loops, exploratory QA passes, compiling E2E traces. The workhorse tier.
  • Frontier model (Opus / Fable) — open-ended judgmentShaping briefs from fuzzy intent, architecture plans, task decomposition, independent code and UX review, adversarial verification of review findings, diagnosing why something is stuck. Rare, deliberate, and worth it.

Escalation rule: a step may move up exactly one rung when it fails, and the escalation is logged with a reason. Nothing routes to a higher tier for mechanical work, and no agent runs before the deterministic checks in front of it pass.

Risk policy — an engine, not a rubric

Technical rules alone misjudge risk: a 40-line change to the checkout flow matters more than an 800-line refactor of the settings screen. But business risk is project-specific, so the toolkit must not hard-code it. The split: the toolkit ships a deterministic policy engine; risk criteria are project-owned data. Three layers, evaluated together, later layers authoritative:

  • Policy engine — toolkitGeneric, deterministic evaluator. Takes a declared surface (plan time) or an actual diff (PR time) plus the brief's structured fields, evaluates every active rule pack, and emits obligations — not just a score.
  • Technical baseline pack — toolkit defaultHard triggers: native surface (ios/, app.config.*, eas.json), SDK/RN bumps, native dependencies, schema/migrations, secrets, and the workflow files themselves (agents never loosen their own gates). Additive factors: new dependencies, widely-imported shared modules, diff size, logic changed without tests. Projects can extend, reweight, or override all of it.
  • Business pack — project-owned, authoritativeA domain map, policy rules, and intake questions authored per project. This is where risk judgment actually lives; the baseline only catches what every RN Expo project has in common.

The domain map — business judgment encoded once

The keystone artifact: a project-owned file mapping business capabilities to code. A human makes each criticality call exactly once ("checkout is critical, settings is not"), and the engine enforces it deterministically forever — which is what keeps business-aware gating on rung L0.

# domains.yml — owned by the project, not the toolkit
checkout:
  description: "Purchase flow from cart through receipt"
  criticality: critical        # a business call, made by a human, once
  paths: ["src/features/checkout/**"]
  screens: ["/checkout/*"]
  scenarios: ["@checkout"]     # E2E scenario tags
onboarding:
  criticality: high
  paths: ["src/features/onboarding/**"]

The same map is reused across the loop for free: post-merge smoke runs a touched domain's scenario tags, the UX Reviewer is told which domain's acceptance bar applies, changelogs group by domain, and trust graduation is tracked per change-class × domain — a class can be graduated in settings while still human-gated in checkout.

Policy rules — obligations, not scores

# policies/business.yml — project-owned
rules:
  - when: domain.criticality == "critical"
    then: [require: G2, block: auto-merge, run: domain-scenarios-pre-merge]
  - when: brief.compliance_impact == true
    then: [require: G2, notify: reviewer]

The engine's verdict is a set of consequences — require G2, block auto-merge, run extra scenarios, notify someone — posted as a factor-by-factor comment (auditable) and applied as labels (the labels are themselves the dispatch events). The low/medium/high score from the baseline pack becomes just one input among the rules.

Intake questions — business risk declared at the source

Each project injects the business-impact questions the Product Shaper must ask during the intake interview: does this change what users pay or see about pricing? Does it touch personal data? Is the behavior change irreversible for the user? Answers become structured fields on the brief, consumed deterministically by the rules above. The person with the idea knows the business meaning of a change better than any diff analysis will.

Cross-check drift detector: the brief's declared impact and the diff's domain footprint must agree. If the brief said revenue_impact: false but the PR lands in the checkout domain, the engine flags the contradiction and escalates — either the brief was wrong or the implementation wandered. Deterministic either way, like the plan-vs-diff scope check.

Unmapped code is a per-project policy choice, and the engine takes no default position: unmapped_criticality is a config value that defaults to null, in which case unmapped files contribute nothing to the criticality of a change (and only apply at all once a domains.yml exists to be unmapped from). A project that wants unmapped code to count sets that value, or lets a logged Haiku call classify the change against the domain descriptions (per the routing policy — and a nudge to grow the map). The engine surfaces domains.unmapped_fraction as a first-class fact, so a project can write its own rule to catch a map that is silently rotting; there is no hardcoded threshold in core.

Policy pack schema — one rule shape for everything

Hard triggers, additive score factors, and business rules are all the same rule shape — they differ only in which obligations they emit. That keeps the engine tiny and every criterion, technical or business, equally injectable:

# policies/business.yml
pack: my-app-business
version: 1
rules:
  - id: critical-domain
    description: "Critical business domains always get human plan review"
    stage: both                  # plan | pr | both
    when:
      all:
        - fact: domains.max_criticality
          in: [critical]
    then:
      require: [G2, human-merge]
      block: [auto-merge]
      run: [domain-scenarios]    # touched domains' @tags run pre-merge

  - id: native-surface           # a "hard trigger" is just a rule…
    when: { fact: diff.files, matches: ["ios/**", "app.config.*"] }
    then: { floor: high, require: [G2], block: [auto-merge] }

  - id: large-diff               # …and so is an "additive factor"
    when: { fact: diff.loc, gte: 800 }
    then: { score: +4 }

Conditions are structured fact/operator trees — all / any / not over a closed operator set (is, in, gte, lte, contains, matches, exists). No expression language to parse: every pack is validatable with a JSON Schema before it runs, and evaluation is trivially deterministic. A readable string sugar can compile down to this form later if needed.

Obligations are a deliberately closed vocabulary of seven verbs: require (G2, human-merge) · block (auto-merge) · run (scenario tags / named checks) · notify · label · score: +N · floor: <level>. Score-to-level thresholds and per-level default obligations live in config, plugging the additive layer into the same vocabulary.

Combination is the safety property: obligations only union — evaluating more packs can only add restrictions, never remove them, so there is no priority arithmetic to reason about. Loosening is explicit and scoped: a project pack may disable or reweight baseline scoring rules by id, but rules the toolkit marks locked: true (the self-modification guard on workflows and the policy files themselves) cannot be disabled by any pack. Agents — and configs — can't unlock their own cage.

Packs are testable. Evaluation is pure (facts in, verdict out), so packs ship with fixture tests run by agentflow policy test — assert the expected obligations against example fact sets. This is how a project safely evolves its risk policy: tighten a rule, run the fixtures, and see exactly which past scenarios would now gate differently. Policy file changes are themselves locked-rule territory, so they always pass a human at G3.

tests:
  - name: "checkout copy change still blocks auto-merge"
    facts: { diff: { files: ["src/features/checkout/Receipt.tsx"], loc: 4 } }
    expect: { block: [auto-merge] }

The verdict is a deterministic JSON document — every rule evaluated, the facts that matched, the union of obligations, the resulting level — rendered as the factor-by-factor comment and applied as risk:* / obligation labels, which are themselves the dispatch events for the next stage. Same engine, run twice: plan time over plan.* + brief.*, PR time over diff.* where the drift.* facts activate.

The orchestrator disappears as a long-running process: GitHub Actions is the orchestrator. Each workflow is stateless, reads everything it needs from the issue/PR, dispatches the right script or agent, and writes results back. Kill anything mid-run and the next event picks up exactly where the labels say things stand.

Entry paths — how a project reaches the loop

The loop is steady-state machinery: every stage is deterministic against a baseline — a domain map, conventions, CI, a bootable app. Establishing that baseline is not a stage; it happens once, before the loop, by one of three paths:

  • Genesis — a new projectA one-shot project-genesis agent (Opus): interviews the human in-session (multi-choice), then establishes the loop's preconditions — app skeleton, repo + labels, config with intake questions, conventions doc, domain map v0, CI — and seeds the backlog with milestone-1 issues in state:idea. That seeded backlog is the handoff: genesis terminates, agentflow-next picks up issue #1, the loop owns everything after.
  • Adoption — an existing appagentflow-init project plus an adoption-audit agent that proposes a domain map draft from the codebase structure; the human confirms each criticality (the one judgment that must stay human). Existing conventions are read, not invented.
  • Steady state — already in the loopThe six stages, as wired above.

Maturity is a fact, not a mode switch: config declares maturity: genesis | steady, surfaced to the policy engine as meta.maturity. A young project — where every change is a new screen, a new dependency, a new domain — would be strangled by steady-state scoring; during genesis, packs soften scoring rules and reserve G2 for locked triggers, while auto-merge stays impossible regardless. Flipping to steady is itself a deliberate human decision: the moment the foundation is declared set.

Human touchpoints

  • G1
    Brief approval/approve comment on the shaped issue. Cheapest place to correct course.
  • G2
    Plan approvalRequired only when the risk engine's obligations say so — driven by the project's own domain map and policy rules; trivial fixes flow through.
  • G3
    Merge approvalNative PR review where agent_identity gives agentflow its own GitHub App to author work as; a SHA-naming /approve comment where it does not, since GitHub forbids approving your own PR. adopt --verify reports which mode a repo is in and why. Graduates toward label-driven auto-merge for proven low-risk classes.
  • G4
    Release approvalA validated /approve G4 comment authorises the release but deliberately does not move the label; agentflow-release then cuts the annotated tag and GitHub Release and performs the verified → released transition only once that release exists — the label follows the artifact, so state:released can never be true with nothing behind it. release_kind decides whether this path runs, the pack's ship adapter does, or the item was already terminal.

Standing rules: interrupt any stage at any time; every agent escalates via notification instead of spinning when its bounded retries run out. Silence always means progress, never a stall. And gates meet the human where they are: in an interactive session, agents collect decisions via multi-choice prompts and post the /approve artifact through the human's own gh account — GitHub is the record, not the conversation; comment-driven approval remains the async path. A pure approval-inbox module collects everything currently waiting at G1, G2, or G4, pairs each item with the exact artifact it should be judged against (the Brief, Plan, or Release comment), and refuses to present an item that has none — so a human working the queue never approves a brief nobody wrote. G3 is deliberately absent from that queue: a merge is judged on the diff, not from a list.

Work and decisions have different authors. Agents author work — branches, commits, PRs, review and verdict comments — as the agentflow GitHub App. Humans author decisions: /approve, review approvals, merges. This is enforced rather than agreed: the gate validator refuses any bot-authored approval before it consults the approver list, and approvers is validated as human logins only. One exception exists, and its authority is the engine's rather than the agent's — G3 on a pull request whose recorded risk verdict already carries no human-merge, no auto-merge block, and demonstrably describes the head being merged. That is precisely the condition under which the loop already merges unattended, so the App transcribes a decision instead of minting one. The verdict reader that adjudicates this rests on a single rule — absence is refusal: a missing, unparseable, or SHA-less verdict, or one computed over different code, authorises nothing. And when the loop does merge unattended it records the merge first and merges second, leaving an authority record that names what allowed it — a record structurally forbidden from ever resembling a /approve line. The App is optional everywhere; a repo without one runs the same loop on the human's own auth.

E2E model — compile once, replay forever

Scenarios are written in Gherkin — behavioral, readable, tagged (@checkout binds to the domain map, @smoke marks the post-merge subset). Underneath the behavioral layer sits a compiled artifact no human writes:

  • First run — the agent interprets (L2). A Sonnet agent reads the step ("When the user taps Checkout"), drives the app through the pack's verify primitives, and emits a compiled trace: the ordered primitive actions with resolved selectors (fixed resolution order: testID → accessibility label → visible text), waits, and assertions. Traces are committed to e2e/traces/ — versioned, reviewable code.
  • Every later run — deterministic replay (L0). The runner replays traces directly against the driver: no model in the loop, fast, zero tokens, identical verdicts. This is the nightly suite.
  • Replay failure — the ladder decides. The trace-deriver agent re-derives the step (one-rung escalation, logged). If it succeeds, the UI changed but the behavior holds: trace updated via PR — which passes G3, so a trace that quietly weakens an assertion still meets a human. If the agent also fails, the behavior broke: evidence bundle → triage → issue into intake.

v1.0 status: the runner core is built and tested — the Gherkin parser, tag selection, trace replay over the execute-step adapter, and needs-derivation emission — and the trace-deriver agent is defined. But both compiling a trace (driving verify) and replaying one (driving execute-step) run through a platform pack's adapters, and pack-expo has not implemented them yet. So this whole model is specified and wired in core but does not run end-to-end until a pack fills the seams.

The economics: tokens are spent only on new scenarios and changed UI — proportional to change, not to suite size. A 50-scenario nightly run on an unchanged app costs nothing. And "flaky selector" vs. "actual regression" becomes a deterministic distinction, not a judgment call.

The per-app config is where projects differ: which flows the nightly sweep walks, what counts as high-risk for G2, which change classes may auto-merge, and any model-tier overrides. The state machine, agents, and interfaces are identical everywhere — that's the payoff of keeping them deterministic, rubric-driven, and platform-blind.

Adoption path — crawl, walk, run

Phase 1 · Crawl — shipped

Scripts + manual dispatch

The L0 layer: state-machine CLI, labels, gate validator, risk engine + facts, verdict reader, run ledger, E2E runner core, agentflow-next. Built and tested; agents run from one local session via /next. This is the deterministic skeleton that runs this repo's own backlog today.

Phase 2 · Walk — mostly shipped

Actions-driven + parallel

The eleven agent definitions, the installer (init labels/project/adopt), the App identity, and the composite Actions (gate-check, risk-verdict, dispatch, post-merge, auto-merge) are shipped. Still open: the pack-expo adapters that let Implementers self-verify in parallel worktrees, and the first real consuming-app loop run. Nightly QA on the self-hosted macOS runner is deferred on cost.

Phase 3 · Run — partial

Graduated autonomy

Verdict-gated auto-merge for proven change classes and auto-pass G2 for low-risk plans are shipped; the installer makes a repo loop-ready in minutes. Headless review (stage 1) runs on a runner today; headless dispatch launch is built but ships off for every state. A second platform pack (web) — the true test of the capability seams — is still ahead.

Build status — v1.0

The deterministic core is built, tested, and runs this repo's own backlog; what remains is the platform pack and the headless stages past review. Unmapped code carries no built-in default: unmapped_criticality is a per-project config value (default null — no contribution, and applied only where a domains.yml exists), and domains.unmapped_fraction is a first-class fact a project can gate on; Haiku classification is opt-in per project. Runner topology: one self-hosted Mac, queued by GitHub Actions concurrency groups (simulator jobs capped at 2); the scale trigger is mechanical — sustained median queue wait above ~10 minutes adds a machine. Interface signatures are specified in interfaces/ — each adapter an executable, JSON on stdin/stdout, shared exit codes (0 ok · 10 recoverable · 20 fatal) feeding the bounded-retry scripts — but no pack implements them yet. E2E: the compile-and-replay model above, core-complete and awaiting those adapters.
